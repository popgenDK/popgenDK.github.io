# AI Instructions for the Albrechtsen Lab Website

This repository contains the Jekyll source for `https://website.popgen.dk/`.
The published branch is `gh-pages`.

## General Rules

- Read the relevant source and data files before editing.
- Preserve the existing Jekyll, Liquid, Bootstrap, and YAML conventions.
- Keep unrelated user changes intact.
- Do not edit `_site/`; it is generated by Jekyll and ignored by Git.
- Install dependencies with `bundle install` and use `bundle exec jekyll build`
  after every substantive change.
- Run `bundle exec jekyll doctor` after configuration, permalink, canonical URL,
  or dependency changes.
- Existing Sass deprecation warnings are expected. Build errors are not.
- Run `git diff --check` before committing.
- Do not commit temporary source notes or editor backups unless explicitly
  requested. Examples include `workInfo.txt` and files ending in `~`.
- Do not commit `_site/`, `.jekyll-cache/`, `.bundle/`, `vendor/bundle/`,
  `.DS_Store`, or other generated local files.
- The custom domain is defined by `CNAME` as `website.popgen.dk`.
- Preserve meaningful `alt` text on every image. Do not add empty links.
- External links opened in a new tab must use `target="_blank"` together with
  `rel="noopener noreferrer"`.

## Updating Publications

The publication list is stored in `_data/publist.yml`. Records are displayed
in file order, so add the newest publications near the top in reverse
chronological order.

Use this Google Scholar profile as the initial comparison source:

`https://scholar.google.dk/citations?hl=en&user=20oVxFsAAAAJ&view_op=list_works&sortby=pubdate`

Google Scholar may block browser tools. A direct public request generally works:

```bash
curl -sL 'https://scholar.google.dk/citations?hl=en&user=20oVxFsAAAAJ&view_op=list_works&sortby=pubdate&pagesize=100'
```

### Publication Policy

- Do not add preprints from bioRxiv, medRxiv, or arXiv.
- Add only final peer-reviewed journal records unless instructed otherwise.
- If both a preprint and journal article exist, use only the journal article.
- Verify title, full author list, journal, year, volume, pages/article number,
  and DOI using a primary publisher page or Crossref.
- Use the final DOI link in the form `https://doi.org/...`.
- Check for duplicates using normalized titles before adding a record.
- Do not copy Google Scholar citation counts into the website.

### Basic YAML Record

```yaml
- title: "Full publication title"
  authors: "Author, A.; Author, B.; Albrechtsen, A."
  link:
    url: https://doi.org/10.xxxx/example
    display: "Journal volume(issue), pages (year)"
  highlight: 0
```

Set `highlight: 1` only for a selected group highlight. Highlighted records
also need an existing image under `images/pubpic/`, plus a useful description:

```yaml
  image: example.png
  description: Short plain-language summary.
```

Optional fields currently used by the site include:

```yaml
  github: https://github.com/...
  software: https://github.com/...
  news1: Markdown links or text
  news2: Markdown links or text
  name: Software name
```

Any record with `software:` appears on the Software page. Such records should
also have:

- `name`: short software name.
- `image`: an existing file under `images/pubpic/`.
- `description`: a concise explanation of the software.
- A valid publication `link.url` and `link.display`.

Spell the field exactly as `software`; misspellings silently hide the entry.

Validate publication changes with:

```bash
ruby -e 'require "psych"; Psych.parse_file("_data/publist.yml"); puts "YAML syntax OK"'
bundle exec jekyll build
```

Confirm new titles occur in `_site/publications/index.html`. Records with
`highlight: 0` should appear only in the full publication list.

## Updating Current Courses

The Courses navigation in `_includes/header.html` contains:

- `Summer CPH` -> `/summer/`
- `Kenya Workshop` -> `/workshop/`
- `Old Courses` -> `/old_courses/`

Keep these URLs stable. Update the page contents rather than changing their
permalinks.

### Summer CPH

The live page is `_pages/summer.md` with permalink `/summer/`.

If the course is not running, replace stale dates, registration details,
instructors, and programs with a short current notice. Link visitors to
`/old_courses/`.

If a new course is announced:

1. Archive the previous live page before replacing it.
2. Update `_pages/summer.md` with confirmed dates, venue, registration,
   organizers, instructors, learning outcomes, and program.
3. Update `_data/summer.yml` when instructor cards are used.
4. Verify all registration and course-material links.

### Kenya Workshop

The live page is `_pages/OIWorkshop.md` with permalink `/workshop/`.
Instructor cards are in `_data/workshop.yml`.

When updating from planning notes:

- Publish participant-facing dates, venue, format, registration, content,
  schedule, instructors, and practical requirements.
- Do not publish internal budgets, flight assignments, private accommodation
  arrangements, or tentative staff logistics.
- Verify instructor names and current affiliations.
- Prefer official institutional or personal lab pages for biographies.
- Download approved portraits to `images/teampic/`; do not hotlink images.
- Use `nopic.png` only when no reliable portrait is available.

Instructor records use:

```yaml
- name: Full Name
  title: Current role and institution
  image: portrait-file.jpg
  description: Current role, research focus, and workshop contribution.
  highlight: 1
  website: https://...
```

## Archiving Courses

Historical course pages must remain unchanged when current YAML data or layouts
change. Archive them as standalone generated HTML, following the existing
patterns:

- `summer2024/index.html`
- `summer2025/index.html`
- `workshop_kenya2024/index.html`

### Archive the Current Summer Page

1. Build the site:

   ```bash
   bundle exec jekyll build
   ```

2. Copy the generated page:

   ```bash
   mkdir -p summerYYYY
   cp _site/summer/index.html summerYYYY/index.html
   ```

3. In the archive HTML, change only:

   - `<title>` to include the year.
   - The meta description to identify it as an archive.
   - The canonical URL to `/summerYYYY/`.

4. Add the archive to `_pages/old_courses.md`.
5. Rebuild and confirm `_site/summerYYYY/index.html` is copied unchanged.

To reconstruct an older version from Git history, find the final relevant
commit and build it in a temporary detached worktree. Do not check out old
versions over the active working tree.

### Old Courses Page

`_pages/old_courses.md` lists both local archive pages and older external course
sites. Keep entries in reverse chronological order within each section.

Use non-indented HTML inside Markdown for Bootstrap cards. Indented HTML can be
rendered as a code block by Kramdown.

## Carousels

Use the shared `stable-carousel` class:

```html
<div id="carousel" class="carousel slide stable-carousel" ...>
```

The rules in `css/main.scss` provide a fixed responsive frame and
`object-fit: contain`, preventing the text below from moving when slides have
different aspect ratios.

When changing slides:

- Keep indicators and slide count synchronized.
- Keep exactly one `item active`.
- Use local images under `images/slider/`.
- Add meaningful `alt` text.

## Navigation

Edit `_includes/header.html` for navigation changes. Follow the existing
Bootstrap dropdown structure used by Courses and EPIC. After rebuilding,
inspect generated pages such as:

- `_site/index.html`
- `_site/summer/index.html`
- `_site/workshop/index.html`

Standalone archives preserve their historical course content unless the user
explicitly asks to update it. Shared quality fixes may still be applied
directly to archive HTML, including broken links, accessibility text, footer
corrections, and compatible security/dependency updates.

## Accessibility and Shared Markup

- Keep HTML that must render directly flush-left inside Markdown files.
  Four-space or tab indentation makes Kramdown emit escaped `<pre><code>`
  blocks, including HTML generated inside Liquid loops.
- Build local asset URLs with Jekyll's `relative_url` filter, for example
  `{{ '/images/pubpic/' | append: publi.image | relative_url }}`. Do not prefix
  local images with `site.url`; relative URLs must work under both
  `jekyll serve` and the production domain.
- Every `<img>` must have meaningful `alt` text. Use an empty alt only for a
  genuinely decorative image.
- Do not create anchors with empty text or empty `href` values.
- Keep the skip link and `<main id="main-content">` landmark in the default
  layout.
- Keep navigation controls labelled with appropriate ARIA attributes.
- Avoid placing Liquid loops inside HTML comments because Liquid still expands
  them. Delete obsolete code or use `{% comment %}...{% endcomment %}`.
- Do not place `<meta>` elements inside Markdown page content; metadata belongs
  in `_includes/head.html`.

## Dependencies and Repository Hygiene

- Keep `Gemfile` and `Gemfile.lock` in sync.
- Use the existing Bootstrap 3 styles unless a deliberate framework migration
  is requested. The current JavaScript is Bootstrap 3.4.1 with jQuery 3.7.1.
- Do not add duplicate layouts, copied Sass files, duplicate image assets, or
  unused large images.
- Confirm a file is unreferenced before deleting it with `rg`.
- GitHub Actions must continue to pass the Bundler-based Jekyll build.

## Verification Checklist

Run:

```bash
bundle exec jekyll build
bundle exec jekyll doctor
git diff --check
git status --short
```

Then verify:

- New pages exist under `_site/`.
- Permalinks and canonical URLs are correct.
- Local images exist and were copied into `_site/images/`.
- Images have meaningful alt text and links are not empty.
- Liquid-generated cards render as HTML rather than escaped code.
- Current pages do not contain stale dates or registration information.
- Archive pages remain available.
- Publication DOI links use final journal records.
- No preprints were added to `_data/publist.yml`.
- Software records render on `_site/software/index.html`.
- No temporary, generated, cache, or local dependency files are staged.

## Committing and Pushing

Before committing:

1. Review `git status` and the complete diff.
2. Stage only intended website files.
3. Exclude temporary notes and backups.
4. Commit with a concise description.
5. Push `gh-pages`.

If the push is rejected because the remote changed:

1. Fetch `origin/gh-pages`.
2. Inspect incoming commits.
3. Rebase onto `origin/gh-pages`.
4. Preserve both remote corrections and local updates when resolving conflicts.
5. Rebuild before pushing again.
